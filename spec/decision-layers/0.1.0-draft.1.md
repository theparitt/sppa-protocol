# Decision Information Layers

**Proposed specification · Document revision 0.1.0-draft.1 · 2026-10-04**

This document organizes the SPPA semantic capability and AI decision standard into
six information layers. Its revision identifies this document, not a new Core wire
version. Core 0.1.1 remains unchanged. Full offers, evaluation, feedback and
reputation are proposed; this document does not claim released schemas for them.

## Purpose and scope

An AI agent needs to distinguish a provider's declared ability, its current readiness,
the terms for a particular job, and evidence from actual work. Keeping these separate
prevents a declared capacity from looking like a free slot, a quoted ETA from looking
like a measurement, or a signed receipt from looking like a quality score.

The layers classify information, not transports, mandatory deployment services or a
universal ordering of trust. They do not create six new protocols. An implementation
can expose them through HTTP, MCP or another declared binding, directly or through
an authorized private registry. A public Hub is optional. The main AI selects;
the Hub supplies candidates/evidence; the provider executes and admits work.

The requirements below define the proposed model. MUST and MUST NOT state its
intended constraints; they do not imply that an existing Core implementation already
implements every layer. Wire conformance remains governed by exact released schemas.

## Layer overview

| Layer | Simple question | Primary producer | Lifetime |
| --- | --- | --- | --- |
| L1 Capability & configuration | What can it do? | Contract author and provider | Versioned definition and configuration revision |
| L2 Runtime status | Is it ready now? | Provider or named observer | Short observation validity |
| L3 Job-specific offer | What are the terms for my job? | Authorized provider offer issuer | Job-bound validity interval |
| L4 Execution & validation evidence | What actually happened? | Provider, caller measurements, validator | Immutable run/check records with explicit scope |
| L5 Evaluation & feedback | Did the result meet the goal? | Authorized caller or evaluator | Versioned assessment bound to a result |
| L6 Aggregated reputation | What do past runs tell us? | Evidence aggregation service | Defined historical window and refresh policy |

L1–L3 describe the present choice. L4–L6 describe observed experience and can inform
the next choice. A caller need not wait for all six layers to exist before using a
Core capability: missing evidence stays unknown, and required evidence fails closed.

## Common identity, scope and provenance

Every layer MUST retain its own source and scope rather than collapse into one
unqualified provider score. The binding authenticates the source and enforces access.
An identity string in JSON is not proof of identity.

| Information | Required meaning when applicable |
| --- | --- |
| Identity | Issuer, provider, capability ID/version and the relevant object ID/revision |
| Scope | Configuration, workload, execution/result, evaluator or aggregation population |
| Time | Observation/publication time, validity or historical window; receiver receipt kept separately |
| Provenance | Provider declaration, observer measurement, validator result, AI judgment or aggregate |
| Evidence | References to authorized source records and their revisions/integrity identifiers |
| Limitations | Unknown, undisclosed, stale, insufficient sample, conflicting or non-comparable data |

Authorization MUST precede disclosure. References, content hashes and matching
capability IDs grant no access. Layers MUST NOT expose confidential job existence,
private artifact matches, caller-specific quotas or reviews to unauthorized readers.

## L1 Capability and configuration

L1 describes result semantics, supported features, input/output roles, parameter
contracts, limitations and declared execution configuration. A semantic capability
definition is distinct from one provider's configuration of it.

Configuration includes concurrency maximum, queue enablement/depth/policy, rate scope,
timeout and retry limits. Implementations MUST bind configuration to a revision or
the corresponding existing exact capability contract. Semantic/contract changes use
the negotiated versioning rules. A queue changing from two jobs to three is an L2
observation and MUST NOT change the capability's semantic version.

A maximum of four concurrent jobs does not establish four currently free slots.
Matching capability IDs or MIME types alone does not prove provider substitutability
or semantic compatibility for composition.

Current coverage: [Core discovery](/sppa-protocol/spec/0.1.1/discovery/),
[capacity declarations](/sppa-protocol/spec/0.1.1/admission/), and the proposed
[semantic architecture](/sppa-protocol/design/architecture/).

## L2 Runtime status

L2 carries source-scoped reachability, service health, admission state, measured load
and freshness. These MUST remain distinct. A healthy busy provider can admit queued
work. A responsive control endpoint does not prove that its GPU workers are ready.

Snapshots bind the exact provider/capability/version, publisher, configuration scope,
observation/expiry times and ordering where supported. Receivers MUST validate identity,
scope, freshness and capacity arithmetic. Missing or hidden capacity is unknown, not
zero. Data derived under a superseded configuration requires refresh or reconciliation.

The experimental [Runtime Status & Capacity profile](/sppa-protocol/design/runtime-status/)
defines heartbeat independence, epochs, sequence gaps and full-snapshot resync.
Its observer adapter checks capacity against the supplied Core execution contract.
Core health already exposes per-capability load. Native heartbeat publication and
subscriptions remain unimplemented.

A heartbeat MUST NOT refresh queue, progress, offer or reputation timestamps.
Queue depth is not job-specific wait time. A snapshot reserves no slot, bypasses no
policy and guarantees no future acceptance.

## L3 Job-specific offer

L3 binds terms to a particular provider, capability/configuration revision, inputs,
parameters, policy/rights and execution assumptions. Offers need immutable identity,
issuer, evidence references, issue time and expiry. A changed binding requires
re-evaluation rather than reuse of the old quote.

Price describes currency, typed billing units, quantity basis, all applicable fees,
estimated total and binding ceiling when supplied. A rate or estimate below the
caller's limit MUST NOT be treated as authority to exceed it. A hard budget requires
an enforceable bound covering applicable charges. Payment authorization, budget
reservation and compute reservation are independent.

Timing separates wait, execution, cold start/setup and transfer. An unknown component
makes an asserted total unknown unless a separately justified total model is supplied.
Models need workload scope, method/source and uncertainty. General queue data cannot
be substituted for a job-bound prediction.

Quote expiry is the deadline for accepting its terms, not necessarily the job's
completion deadline. Selection creates no compute reservation. The provider MUST
recheck authority, terms and atomic admission before committing work.

Current coverage: proposed [AI Decision Contract](/sppa-protocol/design/decision-contract/).
There is no complete released offer/billing implementation in Core 0.1.1.

## L4 Execution and validation evidence

L4 records what happened: admitted job, inputs/parameters, result references, status,
timestamps and execution receipt. Observed wait/runtime are measurements, while L3
ETA remains a prediction. Preserve both to assess prediction error.

Validation is a separate assertion about a specific output and requirements. It
needs validator identity/version, checks performed, measured values, outcome and
evidence. File-integrity checks establish matching bytes; format checks establish
specified properties. Neither establishes usefulness for the caller's goal.

A signature authenticates the signer's assertion and its integrity. It MUST NOT
be represented as proof of independent quality. Provider claims, caller observations
and independent validator findings retain separate sources. A canceled, unresolved
or timed-out run MUST NOT silently become successful execution evidence.

Current coverage: [jobs](/sppa-protocol/spec/0.1.1/jobs/),
[immutable artifacts](/sppa-protocol/spec/0.1.1/artifacts/), and
[signed receipts](/sppa-protocol/spec/0.1.1/security/). The reference demonstrates
hash/size checks and a real FFmpeg result; a general validation family is planned.

## L5 Evaluation and feedback

L5 describes whether the output fits the goal, and what should improve. Assessments
bind an authorized execution/result version, evaluator identity, rubric/version,
dimensions, evidence and limitations. AI evaluation is a judgment, not an automatic
upgrade in trust over measured data or a provider claim.

Distinguish structured usefulness/quality evaluation, caller experience, improvement
suggestion and provider response. Accepting a candidate, reviewing a provider and
authorizing settlement are separate states. A high rating grants no new rights.

Scores MUST retain their scale, workload and rubric. Incompatible rubrics are
non-comparable. Insufficient evidence is unknown; fluent AI commentary alone does
not establish correctness. Revised or disputed feedback retains identity/history
so aggregation can avoid double counting it.

Current coverage: proposed evaluation/feedback requirements in the
[decision contract](/sppa-protocol/design/decision-contract/). No formal released
evaluation, review or reputation family is implemented by Core.

## L6 Aggregated reputation

L6 summarizes authorized historical evidence under a declared aggregation policy.
It MUST identify workload/configuration/provider versions, source classes, time
window, numerator/denominator, samples, exclusions, unresolved outcomes, method
revision and uncertainty. Aggregation cannot turn an opinion into a measured fact.

Reliability, validation pass, quality, price/ETA accuracy and composition success
remain different metrics. Deduplicate execution and feedback references. Preserve
selection bias, correlated evaluators, disputes and provider self-reporting as
limitations; do not equate a hundred correlated reviews with independent runs.

A new provider with no history has unknown reputation, not perfect or zero quality.
Historical success does not refresh L2 status. A new configuration or model may not
inherit scores from a different workload/version without disclosed evidence.

Current coverage: proposed machine reputation; no released aggregation service or
general ranking formula is specified here.

## Policy and authority across every layer

Policy is a cross-cutting eligibility boundary, not a seventh score to average into
quality. Permission, confidentiality, training/logging/retention, location/residency,
license/use rights and spending authority MUST be enforced by trusted authorities.
Unknown facts required for a hard rule do not pass eligibility.

Apply access rules before discovery, offers and historical evidence disclosure, and
recheck at admission and artifact transfer. Ratings and third-party AI suggestions
cannot override a failed rule. Rights in underlying software, models, input, output
and service hosting are separate; wrapper licensing grants none of them implicitly.

## One example across all six layers

**Illustrative data, not collected benchmark results or a live provider offer.**

The caller wants confidential H.264 video conversion, permits queueing and authorizes
at most USD 0.05 for all job charges. Assume privacy and required commercial-use
rights are explicitly allowed under the bound terms.

| Layer | Example observation | What the agent can conclude |
| --- | --- | --- |
| L1 | H.264 supported; maximum concurrency 4 | The declared capability fits; current free slots remain unknown |
| L2 | Fresh healthy snapshot: running 4, waiting 2, queue maximum 8 | Queue-only candidate, if waiting is allowed; nothing is reserved |
| L3 | Wait 20s, run 40s, separately disclosed setup/transfer; provider-enforced all-charge ceiling USD 0.05; quote valid 30s | Consider these job-bound terms; ETA is still an estimate |
| L4 | After execution: wait 25s, run 42s; output passes H.264 check; verified execution receipt | Timing and technical properties are evidenced; usefulness remains unproven |
| L5 | Authorized evaluator rates goal fit 4/5 under a named rubric, with an audio-handling suggestion | A scoped judgment about this result, not a universal quality score |
| L6 | Prior window: 97 of 100 resolved runs completed; 5 additional runs unresolved | Historical reliability for that workload, with unresolved outcomes visible |

L6 describes earlier runs, not a score derived from this single example execution.
New L4/L5 records may inform a future aggregate according to its published method.
If the L2 snapshot expires while a fresh heartbeat arrives, queue readiness becomes
unknown. If required commercial rights are missing, exclude the offer regardless of
the history or rating. If terms expire before admission, refresh and re-evaluate.

## Agent decision procedure

1. Bind human intent and authority; determine semantic capability and required features.
2. Enforce visibility, privacy, rights and other hard eligibility requirements.
3. Validate L1 compatibility and fresh L2 evidence; preserve unknowns and queue consent.
4. Obtain valid L3 job-bound terms with enforceable budget/deadline requirements.
5. Compare applicable L4–L6 evidence, keeping source, uncertainty and comparability.
6. Return candidates, exclusions and unknowns; main AI chooses and records its rationale.
7. Provider rechecks policy, terms and atomic admission; retain idempotency on uncertain calls.
8. Collect L4 observations and authorized L5 assessments; publish L6 only under declared rules.

Observation processing, expiry and heartbeat checks belong in trusted runtime code.
Invoke the main AI when a material choice changes, rather than for every heartbeat.
No universal score or hidden Hub winner is defined.

## Relationship to the seven decision data groups

Layers identify **what kind of assertion a record is**. The existing seven groups
identify **what it is about**. They are complementary, not competing classifications.
An operational value can be an L1 declared limit, an L2 measured queue, an L3 ETA,
an L4 measured duration or an L6 historical accuracy statistic.

| Group | Typical layer relationship |
| --- | --- |
| Technical | L1 semantics/configuration; L4 output checks; L5 goal fit |
| Operational | L1 limits; L2 status; L3 timing; L4 actual timing; L6 historical reliability |
| Quality | L4 validation; L5 scoped judgment; L6 scoped aggregation |
| Economic | L3 prices/caps; L4 usage facts when measured; L6 estimate accuracy |
| Policy | Authority and eligibility across all layers |
| Trust | Provenance across all layers; evidence and aggregation in L4–L6 |
| Reuse | Authorized artifact candidate using L1 compatibility, L3 terms and L4 provenance |

Reuse, composition, payment and streaming use these distinctions where relevant;
they do not acquire authorization merely by appearing in a layer.

## Review and implementation gates

Before claiming the full layered decision model, implementations need versioned
contracts and fixtures for configuration drift, stale runtime, missing rights,
expired/changed offers, inconsistent units, unknown charges, invalid signatures,
unsupported output claims, incompatible rubrics, duplicate feedback and unresolved
historical outcomes. Verify scoped access before publishing any candidate evidence.

Current proof covers declared Core capabilities, health/capacity, jobs, artifacts,
integrity and signed receipts. The isolated runtime profile adds receiver checks.
Full offers, evaluation/feedback and aggregation remain proposed. This specification
organizes their requirements without replacing or altering the archived Core contracts.
