# Job Notifications 0.1.0-draft.1

Status: optional, experimental exact draft. Profile: `sppa.job_notifications`.
Core dependency: `0.1.1`. This extension does not change archived Core contracts.

## Purpose

A caller runtime can wait for long-running work without repeatedly asking for
each job's status. The provider or gateway records lifecycle changes; the runtime
receives them, resumes its agent and verifies the result. An event is evidence of
a reported transition, not proof of correct output and not a way to wake an agent
whose runtime has stopped listening.

## Discovery and capability declaration

A provider MUST place its descriptor at
`manifest.extensions["sppa.job_notifications"]`. Its participating capabilities
MUST include the exact compact capability declaration in their `extensions`
under the same key. A gateway advertises its own descriptor at the same key in
its gateway discovery document. Gateways and providers have different journal
identities and authentication authorities. A caller MUST NOT send gateway
credentials to a provider or treat their cursors as interchangeable.

The descriptor, capability declaration, event and batch MUST satisfy the local
schemas in `schemas/job-notifications/0.1.0-draft.1/`. Different versions require
explicit negotiation. Unknown extension versions MUST NOT be interpreted as this
version. Core-only callers MAY ignore the extension and use Core `job.get`.

## Authority and delivery

The authority derives the owner from bearer authentication, never from caller
query parameters. Both routes MUST expose only that owner's jobs and MUST require
the descriptor's scope when it is non-null. Tokens MUST NOT appear in URLs.
Endpoints MUST use HTTPS, except explicitly permitted local development HTTP;
clients MUST enforce the authorized origin and reject redirects.

`GET http.inbox_url?after=0&limit=50&journal_id=…` returns a batch.
`GET http.events_url?journal_id=…` streams Server-Sent Events. Supply
`Last-Event-ID` to resume. An optional `after` query MUST agree with that header.
Duplicate or unknown query parameters, invalid cursors and limits outside 1–50
MUST be rejected. `limit` is not an SSE parameter. Bearer tokens are headers.

Each SSE frame has `event: inbox`, `id: <next_cursor>` and one JSON `data` batch.
The service sends a batch initially, after committed changes, and while paging a
backlog. Idle heartbeats are SSE comments at least once per second; they are not
job updates. Clients MUST tolerate repeated batches and duplicate IDs, and MUST
persist the cursor only after processing every item in a batch.

Authorization MUST be rechecked while streaming. A revoked or expired credential
closes the stream; implementations MAY first emit `event: auth_expired` with
`{"action":"renew_token_and_resume_from_last_event_id"}`. The runtime renews
credentials using the authority's existing mechanism. This profile does not
define login, provision credentials, authorize job creation or grant billing.

## Journal, replay and gaps

IDs are canonical decimal strings in the range 0–9223372036854775807. They order
commits within one `journal_id` UUID; they do not order provider wall clocks.
An event describes queued, running, completed, failed, canceled or expired work.
`occurred_at` is the reported transition time; `recorded_at` is journal ingestion
time. Sources retain provenance and `result_verified` is always false.
Completed events include a receipt observation URL; other states have null.

Items MUST be ascending, later than `after`, and no later than `next_cursor`.
`latest_cursor` is the journal head, including other owners' invisible commits.
When `has_more` is true, `next_cursor` MUST be the last returned item. When false,
the service MAY advance to the head without revealing other owners' events.
No owner identity or input bytes appear in events. URLs are observation hints;
use the descriptor's job binding and enforce origin checks before following them.

Retention MUST be bounded and declared truthfully. `max_days` equals
`ceil(max_age_seconds / 86400)`. `process` means records can disappear on restart;
`persistent` means journal identity and committed records survive ordinary service
restart, subject to retention. If storage is reset, the identity MUST change.
Readers MAY omit journal_id for a fresh read, but saved cursors MUST be accompanied
by the saved identity. Identity mismatch or a cursor ahead of the journal returns
HTTP 409. Clients MUST reconcile their own known jobs before resetting a cursor.

If an earlier cursor precedes discarded records, `resync_required` MUST be true.
The runtime MUST consult authoritative owned-job snapshots; absence of an event
does not imply completion or failure. `reconcile_url` names the observation route,
not necessarily an enumeration API. Providers need not list all jobs: callers
retain their accepted job IDs. Lost artifacts or missing job records are reported
as unavailable; clients MUST NOT fabricate a successful result.

## Result verification and observation bindings

For `sppa_core_http`, observation is POST Core `job.get` at `url_template`, with
the accepted job ID in a valid Core envelope. For `hub_http`, it is GET with the
job ID substituted into `{job_id}`. Gateways retain their separate delegation
semantics; supporting this notification profile does not make their whole API
Core-conformant. No terminal state is a substitute for a final authoritative
snapshot, output size/hash checks and cryptographic receipt verification.
Receipt validity does not prove output quality.

## Resource limits and error handling

The service MUST bound records, batch size, streams and per-owner streams to the
descriptor limits. The profile caps these at 100,000 records, 50 items/batch,
128 streams and two streams/owner. A stream lasts at most 30 minutes; clients
resume afterwards. Service pressure returns 429 or 503 with bounded retry
guidance. Slow readers MUST NOT create an unbounded in-memory event queue;
implementations pause writes and replay the journal after backpressure clears.
Snapshots are the fallback when SSE is unavailable. Reconnect with bounded
backoff; permanent authentication/contract errors must be surfaced.

HTTP failures return JSON containing `code`, `message` and `retryable`; optional
`retry_after_ms` is milliseconds. No executable instructions, webhook destinations,
UDP delivery or billing mutations are included in this draft. Streaming does not
retry or recreate jobs. The caller's runtime owns reconnection and scheduling.

## Reference implementations and conformance

The protocol reference provider enables this profile by default and offers a
bounded process-local journal; `notifications:false` preserves Core-only mode.
The shared SDK validates shapes and semantic cursor rules and provides an
authenticated SSE/snapshot client. SPPA Hub uses a separate SQLite-backed journal
and gateway observation binding. Neither implies persistent provider artifacts.

Conformance requires discovery and schema validation, owner isolation, all
advertised lifecycle states, immutable terminal transitions, replay, pagination,
gap signalling, identity reset, expired authentication, bounded resource usage
and result verification against the normal execution contract. Schema validity
alone is insufficient. Executable direct-provider tests are in
`test/job-notifications.test.mjs`; Hub integration tests live in its separate repo.
